# 多模态、虚拟场景与交互场景技术交接

本文说明 MarkTool 如何在现有单文件隐式标识之上，实现 GB 45438—2025 的多模态处理、虚拟场景和交互场景。读者可以按本文定位代码、复现测试，并知道哪些地方是标准原文、哪些地方是实现时做的选择。

标准文本以仓库上传的《网络安全技术 人工智能生成合成内容标识方法》（GB 45438—2025，19 页）为准。正文没有“多模态”这一术语。第 3.1 条把生成合成内容定义为文本、图片、音频、视频、虚拟场景等；第 5 章按对象规定显式标识；第 6.1 条和附录 E 规定每个内容文件一份文件元数据隐式标识。

## 合并方式

`818181a` 把 TraceMark 新界面、文本/音频适配器和元数据修复带进了 main。本分支用 merge 接上，冲突只出现在 README、导航、概览、帮助、能力开关和 labeling-backend 说明。后端以 main 的适配器和修复接口为准，多模态模块留在 `app/multimodal`、`app/scenes`、`app/modalities`。

整合决定：

- 删除 `modalities/audio_label.py`。M4A、MP3 改调 `app.adapters.audio`。
- Markdown、PDF、HTML、DOCX 改调 `app.adapters` 里已有的文档适配器。`.txt`、`.vtt`、`.srt` 仍用尾段，因为 main 没有字幕容器。
- `metadata-label-jobs`、`compliance-inspect`、`metadata-repair-*` 的路由和处理函数没有改写。
- 前端以 main 的 `BrandHome`、`Workspace`、`ToolSteps`、`redesign.css` 为准。多模态和场景页放进工作空间，导航项是「多模态」和「场景」。
- Windows 仍用 `start-local.ps1` / `启动最新版.bat` 拉起 8000、8002、5173。没有新增必须单独安装的 Python 包；虚拟场景在 Windows 上使用系统自带的微软雅黑。

## 1. 总体架构与数据流

单文件打标没有改道。JPEG、PNG 仍走 `ImageMetadataService`，MP4 仍走 `Mp4Adapter`，七字段模型仍是 `app/core/aigc.py`，全标签读取仍是 `app/core/reader.py`。新增能力是这些模块的调用方。

```text
CLI  python -m app.cli
HTTP /api/v1/multimodal/*  与  /api/v1/scenes/*
        │
        ├─ 多模态
        │    拆分（ffmpeg）→ 每个成分文件写一份附录 E 标识
        │    → 用未打标副本重组 → 重组结果再写一份标识
        │    → 解析并校验成分和重组结果
        │
        └─ 场景
             虚拟场景：Pillow 把文字画进起始画面 PNG，再走图片适配器写 XMP
             交互场景：界面描述记录文字、位置和持续显示；
                       若附带内容文件，按该文件的模态走上面的单模态写入
```

一次多模态打标的目录如下。`raw/` 是中间文件，不放进给用户的 `bundle.zip`。

```text
out/
  raw/                  未打标的成分
  components/           每个成分一份隐式标识
  recombined/
    composite.mp4       仅视频+音频+文本时：容器上只有一份 XMP
    package.zip         其他组合：根目录只有一个 AIGC.json，载荷不再带标识
  report.json
  bundle.zip            components + recombined + report
```

第 6.1.c 条约束的是**每一个内容文件**，不是压缩包。因此：

- `components/` 里的每个文件是独立内容文件，各有一份标识；
- `recombined/` 里的 MP4 或 `package.zip` 是重组后的那一个内容文件，也只有一份标识；
- `bundle.zip` 是交付档案，里面可以同时有成分文件和重组文件。扫描档案时会看到多份标识，这不表示重组文件违反第 6.1.c 条。报告字段 `compliance_unit` 固定为 `per_content_file`。

## 3. 多模态：拆分、打标、解析、校验

### 3.1 输入

两种入口，不能同时使用：

1. 一个容器文件（通常是 MP4）。服务用 ffprobe 查看流，拆出第一条非封面视频轨、第一条音频轨、第一条字幕轨。没有字幕时，若容器的 `comment` / `description` / `lyrics` / `synopsis` 有实质文本，并且不像 ffmpeg 自己写的编码器标记，则把它当作文本成分。
2. 调用方直接给出 `text`、`image`、`audio`、`video` 中的至少两个文件。

少于两种模态时返回 `NOT_MULTIMODAL`。

### 3.2 成分标识

每个成分调用 `label_file`：

| 角色 | 载体 | 复用的模块 |
|---|---|---|
| video | `mp4-aigc-v1`，`XMP-aigc:AIGC` | `Mp4Adapter` |
| image | `xmp-aigc-v1` | `ImageMetadataService` |
| audio | M4A 为 `m4a-aigc-v1` / XMP；MP3 为 `mp3-id3v2-aigc-v1` / ID3 TXXX | `app.adapters.audio` 的 `M4aAdapter`、`Mp3Adapter` |
| text | Markdown / PDF / HTML / DOCX 用各自已有载体；`.txt`、`.vtt`、`.srt` 用 `text-trailer-aigc-v1` | `MarkdownAdapter` 等，或 `text_label.py` |

Markdown、PDF、HTML、DOCX 与 `/api/v1/metadata-label-jobs` 写进同一位置：frontmatter、XMP、`meta[name=AIGC]`、DOCX Custom XML。字幕和纯文本没有这些容器，分隔序列是 `0x0A 0x1E GB45438-AIGC 0x1E`，后面跟附录 E 的紧凑 JSON。关键词包含 `AIGC`，对应附录 E.a。重组进 MP4 的字幕使用去掉尾段的正文。

MP3 保持 MP3，写入 ID3v2 `TXXX:AIGC`，报告里 `audio_transcoded` 为假。M4A 写 XMP。WAV 等没有适配器的音频才转成 AAC/M4A，并把 `audio_transcoded` 设为真。从视频里拆出的音轨仍放进 `.m4a`；若容器品牌不是 `M4A `，分发层仍选用 `M4aAdapter`，不改变全局 `detect_mime`。

成分文件的 `ProduceID` 写成 `{父编号}-V|A|T|I`。父编号留给重组文件。首次写入时传播编号与制作编号一起加后缀，以保持附录 E 注 1 的对应关系。这是关联约定，不是标准里的新字段。

已有标识策略与单文件相同：`reject` 拒绝，`replace` 先整体删除再写一份。

### 3.3 重组

| 成分 | 重组形态 | 理由 |
|---|---|---|
| 含视频，且不含图片（视频、视频+音频、视频+文本、视频+音频+文本） | 一个 MP4 | 标准的视频文件示例就是单个视频文件。流复制画面和音频，字幕转为 `mov_text`，然后只在容器上写一份 XMP |
| 含图片，或不含视频轨的组合（文本+图片、文本+音频、图片+音频、三者同时、视频+图片等） | zip 包 | 标准没有规定这些组合的单一媒体容器。包根只有 `AIGC.json`，`payload/` 里是去掉标识的成分 |

`AIGC.json` 的文件名包含 `AIGC`，内容是附录 E 字符串。`manifest.json` 只记录成分路径，不再放第二份 AIGC 对象。

### 3.4 解析与校验

解析（`parse_multimodal_path`）只读出标识，不判断是否合规。

校验在写入结束时做一遍，也可以事后对结果包或单个文件再做：

- 每个内容文件恰好一份标识（第 6.1.c 条）；
- 七字段、Label 字符串 `1`/`2`/`3`、字符集（附录 E）；
- 回读对象与计划写入的对象一致；
- 文本的可见正文不变；图片像素不变；音频/视频的轨道和时长不变，并能被 ffmpeg 解码；
- 重组 MP4 的字幕正文不含分隔符，且轨道覆盖当初拆出的视频、音频、字幕；
- 重组包的载荷不再带标识。

`severity` 为 `warning` 的检查不导致整体失败。整体 `passed` 只看 `error` 级检查。

## 4. 虚拟场景

依据第 5.5 条和第 6.1 条。场景包 `virtual-scene.zip` 只有两个成员：

- `start_frame.png`：起始画面，像素里有显式文字，XMP 里有唯一一份隐式标识；
- `scene.json`：绘制参数和条款编号，**没有** `AIGC` 键。

显式标识的实现：

- 文字同时包含“人工智能”或“AI”，以及“生成”和/或“合成”（第 5.5.b 条）；
- 位置只能是四角或四边（第 5.5.d 条）；
- 用系统中文字体把字号放大到文字高度不低于画面最短边的 5%（第 5.5.f 条），放不下则拒绝；
- 文字色和底色对比度不低于 3:1，用来落实“字型应清晰可辨”（第 5.5.e 条）。标准没有给数值，3:1 取的是大号文字常用的可辨门槛；
- 校验时按 `scene.json` 记录的字体、字号、色块重绘，与画面上的色块逐字节比较。这不是 OCR。

未上传画面时生成 960×540 的起始画面。上传图片则在该图上绘制。上传视频时只取第 1 帧做成 PNG，视频本体不放进包，避免包内出现第二个内容文件。

第 5.5.c 条的“可位于持续服务过程中的适当位置”是可选要求。`during_service` 为真时，`service_hint` 记录边或角的位置，供运行时展示。本工具不渲染三维场景。

## 5. 交互场景

依据第 5.6 条。显式标识属于界面，不烧进内容像素。`scene.json` 记录：

- 提示文字，要素与第 5.5.b 条相同（第 5.6.b 条）；
- 一种或多种放置方式：`near_content`、`interface_top`、`interface_bottom`、`interface_background`（第 5.6.c 条）；
- `persistent: true`。标准要求持续显示，关闭则校验失败；
- 文字色与背景色，对比度同样按 3:1 检查（第 5.6.d 条）。

若请求附带内容文件，按 `content_role` 调用 `label_file`，把打标后的文件和 `scene.json` 打进 `interactive-scene.zip`。界面描述里不再放 AIGC 对象。没有内容文件时，隐式标识记为不适用：第 6.1 条作用于内容文件，界面本身不是内容文件。这条检查的严重度是 warning，不单独导致失败。

前端「场景」页用同一套文字、颜色和位置画出预览。预览帮助操作者看位置；是否合规以服务端校验为准。

## 6. 条款对照

| 实现 | 标准条款 | 怎么满足 |
|---|---|---|
| 成分文件和重组文件各写一份七字段 JSON | 第 6.1.a、6.1.b 条，附录 E | `aigc.serialize_aigc`，字段名含 AIGC |
| Label 取字符串 `1`/`2`/`3` | 附录 E.c | `validate_aigc` |
| 生成方、制作编号、传播方、传播编号、两个预留字段 | 附录 E.d–i | 七字段缺一不可 |
| 字符主要来自附录 E.j 的单字节集合 | 附录 E.j | 沿用项目已有的更严 ASCII 子集 |
| 首次写入时传播方与生成方、两个编号一致 | 附录 E 注 1 | `normalize_first_write` 与派生编号 |
| 每个内容文件只留一份文件元数据隐式标识 | 第 6.1.c 条 | 写入后计数必须为 1；重组前去掉成分上的标识 |
| 图片、音频、视频示例所指的元数据位置 | 附录 F.1–F.3 | 图片和视频沿用既有 XMP；音频用 M4A 的 XMP |
| 文本、图片、音频、视频作为不同内容 | 第 3.1 条 | 拆分角色和重组轨道检查 |
| 虚拟场景文字要素、起始画面、边或角、字高不低于 5%、字型可辨 | 第 5.5 条 | `scenes/explicit.py`、`scenes/overlay.py` |
| 持续服务过程中的可选提示 | 第 5.5.c 条 | `service_hint`，不渲染实时三维画面 |
| 交互场景文字要素、内容附近或界面适当位置、持续显示、字型和颜色可辨 | 第 5.6 条 | 场景描述 + 前端预览 + 服务端规则 |
| 内容隐式标识（数字水印） | 第 6.2 条 | 标准写明不做要求，本实现不做 |
| 预留字段中的数字签名示例 | 附录 F.4 | 资料性示例，本实现不写入签名 |

第 5.1 至 5.4 条的文本、图片、音频、视频显式标识**没有**在多模态流程里自动加进字幕、像素或语音。现有单模态能力是隐式标识；本次按任务要求，只为虚拟场景和交互场景实现标准中的显式标识。

## 7. 接口与命令

HTTP 均在 labeling-backend，默认与现有服务一起监听。前端开发服务器把 `/api/v1` 代理到 `8002`。

| 操作 | 方法与路径 |
|---|---|
| 多模态打标 | `POST /api/v1/multimodal/label` |
| 多模态解析 | `POST /api/v1/multimodal/parse` |
| 多模态校验 | `POST /api/v1/multimodal/verify` |
| 虚拟场景打标 / 解析 / 校验 | `POST /api/v1/scenes/virtual/label`、`/parse`、`/verify` |
| 交互场景打标 / 解析 / 校验 | `POST /api/v1/scenes/interactive/label`、`/parse`、`/verify` |
| 下载 zip | `GET /api/v1/composite-bundles/{bundle_id}` |

`request` 是 JSON 表单字段，至少包含 `standard: "GB45438-2025"` 和 `AIGC`。传播方字段可省略，服务会按注 1 补上。虚拟场景的显式参数在 `explicit` 里。命令行示例见根目录 `README.md`。

校验接口在内容不合规时返回 HTTP 200 和 `passed: false`。请求本身不合法（例如显式文字缺少要素、不足两种模态）返回 4xx，不写出文件。

## 9. 设计选择与假设

下列各项标准没有唯一写法。代码按这个选择实现，改动时入口集中，不必改七字段模型。

1. **多模态没有单独的元数据结构。** 拆成内容文件后按第 6.1 条各写一份，重组文件再写一份，并在重组前清除成分标识。
2. **视频+音频+文本重组为 MP4；一旦含图片，或没有视频轨，就重组为 zip。** 标准没有规定画中画或“图片+音频”的单一容器。
3. **成分编号使用后缀 `-V/-A/-T/-I`。** 保证每个内容文件的制作编号不同，又能从父编号追溯。
4. **字幕和纯文本仍用文件尾段。** Markdown、PDF、HTML、DOCX 不再走尾段，改走 main 已有载体。重组字幕时剥掉尾段。
5. **音频复用 main 的 M4A 与 MP3 适配器。** 删除了原先单独的 `AudioAdapter`。只有没有适配器的格式才转成 M4A。
6. **只拆第一条音轨和第一条字幕轨。** 多出来的轨写入 `notes`，不各自成为内容文件。封面图（attached picture）不单独拆成图片。
7. **虚拟场景的合规文件是起始画面 PNG。** 上传视频时只用第 1 帧。持续服务提示只记录，不渲染三维过程。
8. **显式标识校验是重绘比对，不是 OCR。** 字体路径记在 `scene.json`。换机器后若字体文件不在原路径，像素比对会失败，要素和高度规则仍可按记录的字体文件名无法打开而报错。
9. **“清晰可辨”取对比度 3:1。** 阈值常量是 `scenes/explicit.py` 的 `MIN_CONTRAST`。
10. **交互场景可以没有内容文件。** 此时不做隐式标识。附带内容文件时，隐式标识只在该文件里。
11. **多模态不自动添加第 5.1–5.4 条的显式标识。**
12. **字符集继续使用项目已有的严格子集**，不在本次放宽中文机构名。
13. **图片成分的编号登记**使用打标服务存储目录里的 `aigc_identifiers.sqlite3`，与单文件图片打标同一个库。命令行测试应把存储目录指到临时路径，避免写进开发库。

## 10. 局限与后续

- 存储目录下的 `work/` 是请求的临时目录，还没有接入任务保留期清理。结果 zip 在 `output/`，同样没有单独的过期任务。
- 虚拟场景不能校验真实三维引擎里的持续画面，只能校验起始画面和 `service_hint`。
- 交互场景不能从一张界面截图反推文字，调用方需要提交描述。前端预览与描述一致，但是预览本身不上传回服务器。
- 文本尾段不是字幕播放器的通用元数据。直接把打过标的 `.vtt` 当字幕打开，播放器有可能把尾段显示出来。应当使用解析出的正文，或使用重组后的 MP4。
- WAV 等没有适配器的音频会被转成 M4A，采样级波形不会与源文件逐字节相同。报告用 `audio_transcoded` 标明。MP3 不转码。
- 重组 MP4 的画面和音频尽量流复制。虚拟场景因为必须改像素，起始画面是重新编码的 PNG；这与“视频隐式标识不转码”不是同一条路径。
- 附录 F.4 的预留字段签名、第 6.2 条的数字水印、C2PA 都没有做。
- 单文件 `/api/v1/metadata-label-jobs` 已接收文本和音频。多模态调用同一批适配器，不再复制写入代码。

## 10.1 合规检测与修复

多模态页、场景页只负责生成标识。复核改到「合规检测」：

- 请求仍是 `POST /api/v1/compliance-inspect`。只有表单字段 `profile=auto` 时才识别多模态 MP4、结果包、`virtual-scene.zip` 和 `interactive-scene.zip`。不带该字段时，单模态检测与原来一致，无法识别的 zip 仍返回 415。
- 报告沿用合规、不合规、未检出、无法判定。`subject.label` 说明识别出的类型，`units` 按内容文件列出隐式标识份数。场景包另把第 5.5 / 5.6 条的显式问题放进 `issues`。
- 一份内容文件上的隐式标识直接调用单模态的 `classify_records` 和 `RepairPlanner`。完全相同的重复标识保留一份；ReservedCode 缺失或数值 Label 可以确定转换；JSON 损坏、身份字段缺失都不自动修，也不新造 ProduceID。
- 同一内容文件里规范化之后字段值不同的多份标识，收成一个冲突组，挂在报告的 `conflict_groups`。候选 `id` 由组键、读取顺序、标签和规范化内容算出，检测和修复两边一致。来源位置会写成 XMP、ID3、mp4 udta / QuickTime 注释、文本尾段，或场景包里的具体文件。一个上传包里多个内容文件各自冲突时，就是多个组。
- 用户不传选择时，计划不可执行，阻塞原因仍是“多份标识内容冲突，系统不会任意选择其中一份”。单模态在 `metadata-repair-plans` 的 `request` 里传 `selections`（组 id → 候选 id），只有一组时也可以只传 `selected_candidate_id`。多模态和场景在 `composite-repair-plans` 的表单字段里传这两个参数。选定的记录单独交给原来的 `RepairPlanner`，其余冲突份删除后再补预留字段、转换数值 Label。非法 id 返回 422 `INVALID_CANDIDATE_ID`；组没选全返回 422 `SELECTION_REQUIRED`。
- 合规检测页把每个候选排成一行，差异字段高亮。每一组都选中后，「按所选标识修复」才可点。单模态走原来的异步修复任务，多模态和场景走复合修复；完成后下载并自动复检。
- 可执行方案走 `POST /api/v1/composite-repair-plans` 和 `composite-repair-jobs`。这是独立入口，避免把结果包塞进单文件修复任务的指纹和写入器。单模态的 `metadata-repair-*` 不接受这些包。
- 隐式冲突和显式预览分开确认。合规检测页上两块可以同时出现，各自按钮只处理自己的问题；修完一项会下载并复检，剩下的问题留在新报告里。
- 已按用户决定实现：先预览、确认后修复。虚拟场景或交互场景的显式提示不合格时，`POST /api/v1/scene-explicit-previews` 在原起始画面或界面示意上另叠一条符合第 5.5 / 5.6 条的提示，返回稳定的 `preview_id`、左右对比图、位置依据和改动清单，不写回。原位置会挡住原提示或较丰富的画面时，改到最不遮挡的合规位置，并写明依据。原来的不合格提示不删除。
- 真正写回走 `POST /api/v1/composite-repair-jobs`，JSON 里带 `confirm_preview_id`。不带该 id 时，显式问题仍然只报告，方案不可执行。预览保存 24 小时；未知 id 为 422 `INVALID_PREVIEW_ID`，过期为 422 `PREVIEW_EXPIRED`。不能和隐式修复的 `plan_id` 放在同一次确认里。

## 11. 待确认的问题

1. 多模态内容对外展示时，是否还要同时满足第 5.1–5.4 条的显式标识（字幕或正文中的文字、画面边角、语音或“短长 短短”节奏、视频起始画面至少 2 秒）？当前只做了隐式标识。
2. 虚拟场景如果来自一段视频，视频是否也应作为另一个内容文件单独打上隐式标识？当前包内只有起始画面。
3. 成分文件是否应与重组文件使用同一个 `ProduceID`？当前为了“每个内容文件一个编号”加了角色后缀。
4. 字幕和纯文本的尾段是否满足对接方对“文件元数据”的理解？Markdown、PDF、HTML、DOCX 已改用 main 的载体。
5. 含图片的组合是否应生成带画面的 MP4，而不是 zip？
6. 多条音轨、多条字幕、封面图是否都要各自成为内容文件？
7. 对比度 3:1 是否被接受为“清晰可辨”的判定？字高 5% 是否只量字形，不含底色衬块？当前只量字形。
8. 交互场景是否还要保存一张界面截图，并用与虚拟场景相同的像素比对？
9. 预留字段要不要按附录 F.4 写入完整性散列？标准将该附录标为资料性。
10. 单文件打标接口已经开放文本和音频。还需要确认多模态里的尾段文本是否也要改成某一种文档容器。
11. 一个结果包里有的内容文件已标识、有的没有时，总结论目前记为不合规，而不是未检出。单模态没有“多文件里只有一部分有标识”的规则。
12. 已按用户决定实现：先预览、确认后修复。场景显式提示不合格时不再只报告。合规检测生成修复预览，在原画面上另叠一条符合第 5.5 / 5.6 条的提示；原提示保留。用户确认预览 id 之后才写回。
13. 已按用户决定实现。多模态 MP4 的字幕轨尾段和容器标识如果内容一致，仍按重复标识合并，并去掉字幕尾段。若两份内容不一致，检测报告把它们列成同一个冲突组，由用户选择保留哪一份，再覆盖其余冲突份并复检。系统不再自动指定保留容器上的那一份，也不凭空生成 ProduceID。

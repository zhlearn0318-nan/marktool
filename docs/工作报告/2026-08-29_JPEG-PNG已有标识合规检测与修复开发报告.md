# JPEG/PNG 已有元数据隐式标识合规检测与修复开发报告

日期：2026-08-29

开发范围：后端 JPEG/JPG、PNG 文件元数据隐式标识检测、修复计划、异步执行、回读验证、文件保留和审计。

代码状态：仅在本地 `feature/image-metadata` 工作区修改；未提交、未合并、未上传 GitHub。

## 1. 本轮完成内容

### 1.1 统一只读合规检测

新增统一检测器，对 JPEG/PNG 执行以下检查：

1. 文件能否正常解码，实际格式是否为 JPEG 或 PNG；
2. 是否存在 AIGC 元数据记录；
3. 是否只有一份可识别记录；
4. JSON 是否可以解析；
5. 是否具有外层 `AIGC` 对象及固定七字段；
6. 字段类型、必填字段和 Label 枚举是否正确；
7. 项目读取器与 ExifTool 的检出结果是否一致；
8. 编号是否与本地登记内容指纹冲突；
9. 是否存在当前版本无法安全组装的 Extended XMP；
10. JPEG APP11/JUMBF 或 PNG `caBX` 中是否存在 C2PA 特征。

检测结果明确区分 `compliant`、`noncompliant`、`not_found`、`indeterminate`。其中 `not_found` 只表示未发现标识，必须进入普通标注流程，不能作为修复对象。

### 1.2 国标结论和项目限制分离

原实现把 1024 字符上限和首期严格字符范围混入 Schema 结论。本轮将两者拆开：

- `validation`/国标结构结论：只负责外层对象、七字段、类型、必填和 Label 等规则；
- `project_policy`：报告项目自行采用的字段长度、严格字符子集和序列化总字节限制。

因此，登记库查不到编号、出现项目不支持的字符或存在 C2PA，都不会被错误表述为“国标不合规”。它们会作为来源可信度、项目处理能力或保护性限制单独报告。

### 1.3 两阶段修复流程

修复没有直接复用普通 `replace` 操作，而是增加两阶段接口：

1. 上传原文件并生成只读检测结果和修复计划；
2. 用户核对字段变化、输入哈希和计划哈希后，明确确认并创建异步修复任务。

计划与原文件 SHA-256、检测结果和拟写入结果共同绑定。确认时再次检查原文件 SHA-256，避免确认后文件被替换。修复输出保存为新文件，不覆盖用户原文件。

### 1.4 自动修复边界

在不猜测业务语义的前提下，仅允许生成以下可确认计划：

- 旧版内层对象补外层 `AIGC`；
- 整数 Label 1/2/3 转为等值字符串；
- 缺失的 `ReservedCode1`、`ReservedCode2` 补空字符串；
- 完全相同的重复记录去重；
- 使用用户明确提供且通过校验的可信七字段整体替换旧记录。

以上动作仍需用户明确确认。缺失的机构、编号和 Label 不会自动生成；冲突重复项不会任意选择；损坏 JSON 没有可信来源时不处理。

### 1.5 异步任务、回读和审计

修复任务沿用现有异步任务风格，并增加：

- 写入后由独立合规检测器重新检查；
- 确认最终只有一份记录；
- 确认七字段与计划完全一致；
- 确认图片像素指纹不变；
- 记录操作标签、确认方式和 `identity_verified=false`；
- 用 SHA-256 前后链接保存追加式审计事件；
- 以内容哈希命名长期保存原始标识、检测结果、拟修复结果和最终校验信息；
- 原文件和结果文件保留 180 天，过期只删除文件，长期审计内容不删除。

正常新增标注接口原有 7 天保留期未被修改。

## 2. 测试结果

新增测试覆盖：

- `not_found` 拒绝创建修复任务；
- 国标结论和项目字符限制分离；
- 缺失保留字段补空计划；
- 编号与已登记内容冲突时禁止修复；
- 相同重复项可确认去重；
- 冲突重复项必须人工复核；
- 损坏 JSON 需要可信来源；
- PNG `caBX` 和 JPEG APP11/JUMBF 的 C2PA 存在性拦截；
- 普通非 C2PA APP11 不被误判；
- `confirmed=false` 和错误计划哈希不能执行；
- JPEG、PNG 真实 ExifTool 端到端修复；
- 原文件不变、输出唯一、七字段一致、像素一致；
- 180 天文件清理后，长期审计文件和哈希链仍保留。

最终全量回归结果：`141 passed in 27.45s`。其中 JPEG/PNG 写入、回读和修复端到端测试使用本机真实 ExifTool；只在“交叉读取器故障/分歧”异常分支测试中使用了可控测试替身，以稳定触发错误条件。人工联调发现漏存任务编号后不便找回，因此又为计划查询响应补充了关联 `job_id` 和任务链接，并完成回归验证。

## 3. 没有照搬原改进方案的部分及原因

本节为重点说明。以下差异是为避免误修、与现有架构冲突或虚构来源而主动保留的边界，不是遗漏。

### 3.1 没有把“登记库查不到编号”判为国标不合规

登记库只包含本系统已经登记的数据，不能代表全行业完整记录。查不到只能记为 `unverified`，不能证明文件违反国标；只有同一机构和编号已经绑定到另一内容指纹时，才作为项目来源冲突禁止自动修复。

### 3.2 没有自动生成或猜测缺失的身份字段和编号

ProduceID、PropagateID、生产者、传播者和 Label 都具有业务含义。来源未知时自动生成会制造虚假溯源信息，因此系统宁可保留为人工复核，也不凭空补值。`ReservedCode1/2` 补空是例外，因为补空不引入新的机构或身份事实，并且动作会在计划中明确展示后由用户确认。

### 3.3 没有对所有重复项直接“保留第一份”

只有规范化后内容完全相同的重复项可以生成去重计划。内容冲突时保留第一份没有可信依据，可能删除真实记录，因此必须人工核实或提交可信七字段来源。

### 3.4 没有对 C2PA 做签名验证或自动重签名

当前只按官方承载位置检查 C2PA 是否存在：JPEG 为 APP11/JUMBF，PNG 为 `caBX`。原因是完整验证还需要 C2PA 清单解析、签名、证书链、信任列表和时间信息；现有仓库尚未集成相应 SDK 和信任策略。错误实现比明确停止更危险，因此本期发现 C2PA 后禁止自动改写，并标记 `present_unverified`，不声称签名有效或无效。参考：[C2PA Technical Specification 2.4](https://spec.c2pa.org/specifications/specifications/2.4/specs/C2PA_Specification.html)。

### 3.5 没有实现 Extended XMP 完整分片重组

仍采用“检出后停止自动处理”的保守方案。完整实现需要处理 GUID、总长度、偏移、乱序、缺片、重复片和引用关系；首期自行实现容易漏检旧标识并造成覆盖。待团队决定采用成熟库或补齐规范测试后再开放。

### 3.6 没有原地覆盖文件或只保留一个 `.bak` 备份

修复输出为独立新文件，服务端原件和结果保留 180 天，关键元数据与审计长期保存。原因是原地覆盖加单个备份容易被后续操作覆盖，且不能满足多次审计需要；独立输出更适合异步接口和多人协作。

### 3.7 没有把历史记录重新塞回当前文件

国标要求当前文件仅保留一份文件元数据隐式标识。历史原始值、计划、结果哈希和操作事件存放在外部 SQLite 审计表及内容寻址 JSON 中，不在媒体文件内叠加多份 AIGC 记录。这样同时满足当前文件唯一性和历史追溯需求。

### 3.8 没有接入账号体系，操作人身份仍未验证

当前只保存 `operator_label`，并明确记录 `identity_verified=false`。原因是仓库没有统一登录、角色或权限系统，图片分支单方面增加认证方式会与前端和其他模块冲突。正式上线前必须由团队统一接入鉴权；当前接口仅用于受控环境。

### 3.9 没有改成分布式任务、对象存储或多 Worker

当前沿用单机线程池、SQLite 和本地目录，并把修复 Worker 固定为 1。原因是这与现有仓库架构一致，便于首期联调；贸然增加 Redis、Celery、PostgreSQL 或对象存储会扩大部署范围。生产化时应统一升级基础设施。

### 3.10 没有修改前端和其他媒体类型

本轮只提供稳定后端接口和 Swagger 测试入口，不修改前端页面，也不扩展视频、音频、文本、显式标识或水印。原因是当前分工限定为 JPEG/PNG 后端元数据适配器和测试，避免覆盖其他成员代码。

## 4. 尚需人工确认的事项

1. 团队是否接受当前 API 路径、字段命名和两阶段确认形式；
2. 前端由谁实现字段变化对比、风险提示和确认按钮；
3. 正式账号体系接入后，如何将用户 ID、角色和认证结果写入审计；
4. 180 天文件保留及长期审计保留是否符合团队最终存储预算和隐私制度；
5. C2PA 后续采用何种官方/成熟 SDK、证书信任策略和签名重建方案；
6. Extended XMP 后续是继续拒绝，还是引入成熟解析库；
7. 生产部署采用何种数据库、任务队列、对象存储、下载鉴权和监控系统。

## 5. 结论

本轮已经形成“只读检测—修复计划—明确确认—异步写入—独立回读—外部审计”的完整后端闭环。自动处理边界以“不猜测来源、不覆盖原件、不破坏未知 C2PA/Extended XMP”为优先原则，并与现有仓库异步接口和 JPEG/PNG ExifTool 适配器保持一致。

该实现可以作为当前受控开发环境的可测试版本，但在账号鉴权、C2PA 完整验证、Extended XMP、分布式存储和正式第三方合规认证完成前，不应表述为生产级全面合规系统。
